# 多维表格与自动化竞品分析报告（ArcoVue vs 飞书 / 钉钉）

> 版本：v1.5.1 | 日期：2026-08-29 | v1.5 工作台/仪表盘；**v1.5.1 严格对照 web/src 复核 §6 缺口清单**（筛选下推、右冻结、AI 附件、历史 diff）

## 1. 概述

本报告对比 NewLife.Cube.ArcoVue 与飞书多维表格、钉钉 AI 表格在多维视图与自动化领域的能力，并补充相对典型企业中后台皮肤（若依 / JeecgBoot / Ant Design Pro / Arco Design Pro）的差异，输出缺口清单与落地建议。

对比目标不是复刻协作产品，而是吸收对 Cube 管理页有价值的能力。飞书/钉钉是「表格即产品」的数据协作平台；ArcoVue 是「表格即实体管理界面」的 .NET 中后台默认皮肤。

### 1.2 ArcoVue 实现基线（2026-08-29 审计）

- **六视图**：table / tree / card / kanban / calendar / gantt。甘特只读（OSC-0019）；看板/日历无拖拽写回（方案内刻意不做）。
- **ViewProfile 后端权威**：命名视图 / 列 / 排序 / 映射 / 筛选记忆 / 分组 / 预定义查询 / FormJson / 全局模板（个人 > 模板 > 系统）。实体 **无角色层**（与首页工作台分层分开）。
- **页面仪表盘**（OSC-2608280e9e）：`InsightPanel` = `WidgetHost`；`DashboardJson`；洞察槽主推 metricCard / miniChart；跨实体须授权。
- **首页工作台**（OSC-26082815a1）：`/home`；**用户 HomeJson > 主角色 Parameter > 系统种子**；`/Admin/Index` 仍监控页；支持全屏（暗色 bg-1 叠 fill-2）。
- **查询双轨（待收口）**：`SearchDrawer` + `QueriesJson` → 服务端 `GetList`；筛选构建器已 **`viewFilter` 下推**（OSC-260819e483 P2）+ 本页 `matchesViewFilter` 复核兜底（后端忽略时翻页仍可能不完整）。§8.5.4 退役搜索产品面——**尚未实施**。
- **右抽屉三 Tab**：表单 / 历史（分页+动作筛；`parseRemarkDiff` 启发式字段 diff）/ 评论（两级，无 @）。
- **自动化**（OSC-260815fa86）：线性 GraphJson + C# 执行器，**不是** FlowGram；含删除触发。
- **壳与协作**：SSO/多租户/MFA、side·top·mix·embed、TagsView、外观、Inbox、条件填色、批量启停、AI 浮窗（**含附件**；无会话历史列表）、ShareView 短令牌、**列左右冻结**。
- **测试**：约 **78** 个 `*.spec.ts` + Playwright 3 spec；组件测试仍为 0（无 `@vue/test-utils` / 无测 `.vue`）。
- **草稿/未创建**：OSC-0018、OSC-2608273d95 Draft；OSC-0010 / 0011 未创建。

### 1.3 v1.0 → v1.1 主要修正

| 原判断 | 修正 | 依据 |
|--------|------|------|
| 钉钉「能力约为飞书的子集」 | 过时。现品牌为 **AI 表格**，官方已具备六视图、仪表盘、工作流、双向关联、公式、查找引用、高级权限、AI 字段 | table.dingtalk.com、help.dingtalk.io |
| 飞书有「树表」一等视图 | ❌。官方六视图为表格 / 看板 / 日历 / 甘特 / 画册 / 表单，无树表 | 飞书帮助「快速上手多维表格」 |
| ArcoVue 画册 ❌、飞书树表 ✅ | 改为：ArcoVue 有 **卡片流**（非以图为主的画册）；飞书/钉钉有画册、无树表 | 代码 OSC-0006/0007；官方视图列表 |
| 「筛选服务端化 ❌」一刀切 | 拆开：高级搜索 / 预定义查询已服务端化；缺口仅筛选构建器 | OSC-0015 design、`effectiveSearch` vs `viewFilter` |
| 8 类动作却列出 9 个名字 | 执行器 9 类；菜单 8 项（无 `runAutomation`） | `automationGraph.ts`、SPA-20 |
| 钉钉 AI 文本 ❌、关联仅单向、仪表盘 ⚠️ | 钉钉官方有 AI 字段/助理、双向关联、仪表盘、工作流 | 钉钉字段表 / 快速上手 |
| 飞书自动化「编辑器内立即执行 ✅」 | 改为 ⚠️。官方路径是沙箱 + 按钮触发 + 运行日志，帮助中心未提供编辑器「立即运行」 | 飞书「使用自动化流程」「使用沙箱」 |
| 公式 / 查找引用列为 P0 | 与迁移方案 **§8.2.6 非目标**冲突；降为「定位外、需先重开决策」 | 迁移方案 §8.2.1 / §8.2.6 |
| 历史「筛时间/用户/动作」 | 仅分页 + 动作筛选；无时间/用户筛 | `useRecordDrawer.ts` |
| 飞书删除触发 ✅ | 飞书工作流/自动化 **不支持删除触发与删除动作**；此点 ArcoVue 反而更全 | 飞书「工作流和自动化常见问题」 |

## 2. 竞品概览

| 项目 | 类型 | 技术栈 / 交付 | 定位 | 备注 |
|------|------|--------------|------|------|
| **NewLife.Cube.ArcoVue** | 开源皮肤 | Vue 3 + Arco Design Vue + VisActor VTable；数据在自有 Cube / XCode 后端 | .NET 企业中后台默认皮肤：元数据驱动 CRUD + 多维视图 | 固定容器 + 有限用户运行时自定义；代码级 Section / apps 覆写；工作台三级解析 |
| **飞书多维表格** | 商业 SaaS | 云端 Bitable | 新一代多维数据协作平台（表格即数据库） | 对标交互范式；自动化 + **工作流画布**双轨；仪表盘独立对象 |
| **钉钉 AI 表格** | 商业 SaaS | 云端；深度绑钉钉通讯录 / 待办 / 审批 | 「AI 时代的应用搭建平台」（2025 起由多维表格升级） | 与飞书能力同级，壁垒在组织通讯录与 OA 闭环，不再是「飞书子集」 |

**定位差异**：飞书/钉钉卖的是多人实时协作的可视化数据库；ArcoVue 卖的是「实体 + `EntityController` + 菜单 → 完整管理页」。吸收清单必须过三道门：① 不破坏 GetPage / Cube 权限契约；② 不引入画布 / Widget 市场（§8.2.1 明确不做）；③ 对企业中后台运维/审计有直接收益。

### 2.1 相对典型企业中后台皮肤（定位对照）

| 维度 | ArcoVue（代码事实） | 若依 / Jeecg / Ant Design Pro / Arco Pro（常见形态） |
|------|---------------------|------------------------------------------------------|
| 页面来源 | **元数据驱动**：新实体 + `EntityController` → 自动列表/表单/搜索 | 多为代码生成器或手写 CRUD 页；Jeecg 有 Online 表单，模型不同 |
| 多维视图 | 六视图 + **树表一等公民** + ViewProfile 后端持久化 | 多为单表 + 少量树表；少见看板/甘特/日历一体 |
| 首页 | 用户 > 主角色 > 系统 Widget 墙（非租户层） | 常见静态仪表盘或角色菜单首页，少见三级 Widget 墙 |
| 自动化 | 实体内嵌线性自动化 + .NET 执行器（含删除触发） | 常依赖外部工作流/定时任务；少见嵌在实体列表的 GraphJson |
| 扩展 | Section / apps 代码覆写；禁止运行期 Widget 市场 | 低代码设计器 / 插件中心较常见 |
| 差距（勿吹） | 无页面设计器、无 i18n、无微前端多应用、看板不可拖改 | 生态模板与社区示例通常更全 |

## 7. 权限契约（增强元数据时不可破坏）

Cube 的安全模型是「菜单动作 + 行级过滤 + 分区字段集合」，不是飞书式「表/视图/字段/记录」一张高级权限表。任何后端增强必须继续满足：

| # | 契约 | 含义 |
|---|------|------|
| 1 | **GetPage 是 SPA 字段权威** | 某字段是否存在于 list / addForm / editForm / detail / search，只由控制器 `OnGetFields` + XCode `ShowIn` 决定。`FormJson` / `ColumnsJson` / 命名视图只能改顺序、显隐、分组折叠，**不能**增字段、改 `ReadOnly`/`Nullable`/`ItemType`、也不能授权写入。 |
| 2 | **CRUD 权利来自菜单 `PermissionFlags`** | Detail=1、Insert=2、Update=4、Delete=8，由 `EntityAuthorize` 拦在 Action 上。UI 的 canAdd/Edit/Delete 来自 `Auth.Info` / `MenuTree` ∩ `setting.enableAdd` ∩ `!isReadOnly`。不要在 GetPage 里另造一套 ACL 却不在写入路径强制。 |
| 3 | **行级 PERM-6 只在服务端生效** | `DataPermissionAttribute` + 租户 `CreateWhere` 进入 `SearchData` / `FindData`。前端筛选、ViewProfile.filter、预定义查询都不是安全边界。 |
| 4 | **唯一写通道** | `POST`/`PUT`/`DELETE`/`EnableSelect`/`DisableSelect`（及将来的批量改字段）必须 `FindData` + `Valid` + `OnInsert/OnUpdate`。禁止 ViewProfile、筛选 AST、公式表达式变成写入口。 |
| 5 | **列表可见性 = 分区数组成员** | `DataField.Visible` 默认 false 且 `Fill` 从不置 true，**不能**拿它当列表过滤条件。 |
| 6 | **GetPage / GetFields 当前 `[AllowAnonymous]`** | 字段名、类型、LOV 码对未登录也可读。敏感默认值、权限表达式、公式原文若含业务规则，不要塞进匿名元数据；做字段级权限时 GetPage **必须改为按当前用户裁剪**。 |
| 7 | **Map/LOV 是标签，不是可写关联列** | `BatchLabel` / `DataSourceMap` / `Entity.{Type}` 只解决显示名。写回仍是外键本身。 |

## 8. Cube 后端元数据需要增强的地方

对照 `DataField` / `GetPage` / 默认 `Search(Pager)`（`ReadOnlyEntityController`、`EntityController`、`FieldCollection`）。下面只列**协议与元数据**缺口：皮肤已独自完成的（填色、**左右冻结**、i18n 仍缺、AI 浮窗+附件）不重复展开。

### 8.1 现有元数据基线（不必推倒）

| 能力 | 已有 | 皮肤侧注意 |
|------|------|------------|
| 五分区字段 | `GetPage`：`setting` + `list`/`addForm`/`editForm`/`detail`/`search` | 搜索分区是 UI 字段清单，真正 WHERE 以 `Search(Pager)` 为准 |
| 字段形状 | `Name`/`DisplayName`/`Category`/`TypeName`/`ItemType`/`Length`/`Nullable`/`PrimaryKey`/`ReadOnly`/`MapField`/`LovCode`/`DataSourceMap` | `Required`、`Authority`、`Extended1~3` 已序列化但 **Fill 未赋值、Cube 未消费** |
| 列表扩展 | `ListField.Url`/`DataAction`/`TextAlign` 等会下发 | `GetValue`/`GetClass`/`DataVisible` 为委托且 `JsonIgnore`，SPA **拿不到** MVC 计算列/行 CSS |
| 行权限 | `DataPermissionAttribute` | 不出现在 GetPage |
| 关联名 | Map `SetRelation`；大表 `LovCode=Entity.*` + `POST /Admin/Lov/BatchLabel` | 只能显示映射字段（通常是名称），不能声明「再带出关联表其它列」 |
| 启停批量 | `GET EnableSelect/DisableSelect?keys=`，需 Update + `Enable` 列 | 不是通用批量改字段 |
| 局部更新 | `PUT` → `CopyFrom(..., true, true)` → XCode 脏字段 | 无独立 PATCH；客户端若提交完整对象，行为取决于模型绑定 |
| 搜索 | `Q`、`dtStart`/`dtEnd`、`{Field}=value` **Equal**、单列 `sort`/`desc` | 控制器重写 `Search` 时常常丢掉通用 Equal（Department 等），这是 OSC-0015 改前端过滤的根因 |
| 图表 | `GET GetChartData`，与列表同一套 `SearchData` | 默认 `OnGetChartData` → `[]`；GetPage **没有**图表元数据 |
| 校验 | `ValidateEntityFields` 用 `!Nullable` + `Length` | WebAPI `EnableFieldValidation` **默认 false**（注释仍写默认 true），等于协议有、门默认关 |
| 审计 | `LogOnChange` → `WriteLog(entity)` | Remark 已是 `Field=old -> new`（P4：前端解析，不改写入） |
| 评论 | `/Cube/EntityComment` 同表回复 | 无提及人列表 |

### 8.2 必须改后端才能安全落地的缺口

#### （1）筛选 AST 进 `SearchData`（缺口 #5）

默认 `Search` 只做关键字、主时间区间、字段等值。筛选构建器的 12 个操作符与 AND/OR **没有**服务端编译器。

增强要点（契约内）：

- 查询增加封闭结构（可复用 `ViewFilter`：`logic` + `conditions[]`），由 `SearchData` 编译为 `WhereExpression`，再 **AND** 到 `CreateWhere()` 之后。数据权限表达式不可被 OR 掉。
- 字段白名单：`Factory.Fields` ∩（GetPage `search` ∪ `list` 中的真实列）。拒绝未知字段、拒绝原始 SQL、`OrderBy` 同样白名单。
- 组合点必须放在 `SearchData` 而不是只改默认 `Search`：大量控制器整段重写 `Search` 且不调用 `base`。应提供 `ApplyRequestFilter(p, ref where)`，重写方必须并入；未并入则文档与单测视为违规。
- 分页在数据库侧完成后再返回。前端 `matchesViewFilter` 可保留为幂等复核，不再是唯一实现。

#### （2）字段级权限（缺口 #6）——真正的元数据缺口

现状：`ReadOnly` 来自 XCode 静态特性；`Authority` 空置；`DataVisible` 不能下发。角色看不见某列，今天只能靠控制器 `RemoveField`（全局）或前端藏列（可被 GetPage/GetDetail/导出绕过）。

增强要点：

- **不要**用 NamedView / `ColumnsJson` 充当 ACL（缺口 #19 同理：角色模板是呈现分层）。
- 按当前用户裁剪五分区：无读权的字段从 list/detail/search 消失；无写权的出现在 detail 但 `ReadOnly=true`，且不进 addForm/editForm。
- 写入路径对称：`Insert`/`Update`/`EnableSelect`/将来的批量改字段/导入/导出，丢弃或拒绝不在本角色 editForm 内的属性。否则前端藏列毫无意义。
- GetPage 改为登录用户上下文输出（匿名只给登录页需要的最小 schema）。现在的 `[AllowAnonymous]` 与「按角色藏薪资列」不能共存。
- 存储上优先「角色 × 实体 × 字段 × 读/写」或控制器可重写的 `FilterFieldsForUser`，避免把权限表达式写进匿名 JSON。

视图级权限（「这个命名视图谁能打开」）建议 **不做**：菜单已经控制谁能进实体；再给 ViewProfile 做 ACL 会变成第二套授权。最多做管理员发布的只读模板（OSC-0014 已有）。

#### （3）通用批量改字段（缺口 #3 的后半）

`EnableSelect` 只覆盖 `Enable`。批量改负责人/状态需要新 Action，但必须逐行 `FindData`（行权）+ 字段 ∈ 当前用户 `editForm` 且 `!ReadOnly`（列权）+ `OnUpdate`（校验与自动化入队）。禁止一条 SQL `UPDATE ... WHERE Id IN (...)` 跳过实体钩子。

#### （4）审计 diff 与评论提及（缺口 #8 / #9）

- Log：`WriteLog("Update", entity)` 已把 Dirtys 写成 `Field=old -> new`。历史 Tab 按字段名解析即可；值含逗号时回退原文。不要再包一层 JSON。
- `EntityComment`：增加提及用户 ID 列表；发表时写 `NotificationRecord`。`Content` 继续纯文本即可，不必上富文本。

#### （5）单元格 PATCH 白名单（缺口 #7）

现有 `PUT` 已能脏更新，行内编辑可以先走它。更稳的契约是 `PATCH { id, values }`：只接受 `editForm` 中非只读字段的子集，先 `FindData` 再 `SetItem`。避免客户端为改一个状态而提交整张表单被 `CopyFrom` 带上未展示字段。

### 8.3 弱项：协议已有、元数据不完整

| 项 | 问题 | 建议 |
|----|------|------|
| 图表（缺口 #2） | GetPage 不声明有哪些图；默认 `OnGetChartData` 为空 | 可选：`setting.charts` 或按枚举/主时间的**约定默认图**（计数、时间趋势），仍走同一 `SearchData`，不引入用户自定义 ECharts option |
| 列表 `stat` | `Index` 把 `p.State` 当作 `TEntity`；`SearchData` 在有数据权限时把 `WhereBuilder` 塞进 `p.State` | 统计对象与权限 builder 分槽，否则洞察区「总数」契约不稳定 |
| 必填 | `Required` 不下发；校验看 `Nullable` 且默认关闭 | `Fill` 时 `Required = !Nullable`；WebAPI 默认打开 `EnableFieldValidation`（与注释一致），子类再关 |
| 多级排序 | Pager 单列 `sort`/`desc` | 接受白名单 `sorts=Name,-Id`，编译为 `OrderBy`；禁止客户端任意 `OrderBy` 字符串 |
| 导入 | CubeNC 有公开 `ImportFile`；WebAPI `EntityController` 导入方法是 protected | SPA 导入若作为产品能力，WebAPI 线需公开 Action，权限与字段白名单同更新 |
| 人员控件（缺口 #14） | 筛选侧已有创建人启发式 + `/Admin/User` | 可选 `ItemType=person` 明示，避免靠字段名正则 |

### 8.4 重开 §8.2.6 才动的元数据（缺口 A / B / D）

这两项一旦做，必须是 **只读投影**，不能变成用户可写的虚拟列。

**只读计算列（A）**

- `ListField.GetValue` 不能进 SPA。需要可序列化的声明：例如 `ItemType=formula` + 封闭表达式（列算术/日期差），服务端在列表/详情求值。
- 计算列强制 `ReadOnly`，不进 addForm/editForm，不进 `CopyFrom`/`PATCH`。
- 禁止任意 JS/SQL。复杂规则继续写 C# 扩展属性（扩展属性本来就会出现在实体 JSON 里）。

**只读查找引用（B）**

- 今天 Map 把外键换成关联显示名；`BatchLabel` 补的也是名称。缺的是「再带 Customer.Level、Customer.Region」。
- 建议在 Map 字段上增加 `LookupDisplays[]`（关联实体字段白名单），GetList/GetDetail **附加**只读列（`CustomerLevel` 等），不替代外键，不提供反向写回。
- 双向链接、在关联表自动建反向列：与实体模型冲突，维持不做。

**甘特依赖（D）**：不是 GetPage 字段问题，而是任务实体要有前置任务外键（或关系表）。有模型之后甘特只读渲染依赖线，写回仍可不做。

### 8.5 明确不要放进元数据的东西

| 不要 | 原因 |
|------|------|
| 把 `NamedView.filter` 当权限 | 用户可清筛选 |
| 条件格式规则当敏感列保护 | 颜色能藏不能防导出 |
| 在 GetPage 下发 `DataPermission` 表达式 | 匿名接口 + 泄露行权规则 |
| 用户自定义工作流 / 公式脚本 / 跨实体查询引擎 | 迁移 §8.2.1 / §8.2.6；写通道会失控 |
| 用 `Authority`/`Extended*` 偷带未文档化语义 | 已空置；安全相关应显式属性 + 写入路径强制 |

## 9. 结论与建议

**ArcoVue 应继续保持的优势**

1. **数据自主可控**：实体即库表，逻辑可写 C#——SaaS 多维表做不到。
2. **元数据驱动零前端 CRUD** + Section/apps 代码级扩展；相对若依/Pro 少造每页脚手架。
3. **树表一等视图**（飞书/钉钉官方无）；贴合组织/分类实体。
4. **自动化触发面完整**（含删除触发、`aiText`），执行器在服务端可编程。
5. **三级首页工作台 + 页面仪表盘 Widget 协议**（用户>主角色>系统；洞察与工作台 surface 分离）——典型中后台皮肤少见。
6. VTable 大表性能、ViewProfile 命名视图、全局模板、embed 短令牌、AI 浮窗与站内信，结构层已齐。

**差距本质**

结构（多视图、命名视图、搜索、线性自动化、工作台/仪表盘）已齐。剩余缺口：

1. **方案内债**：**查询收口**（§8.5.4：退役 SearchDrawer/QueriesJson + 筛选全控制器可靠下推）是当前最高优先；其次 i18n / 组件测试。
2. **内容可读**：默认图覆盖率、只读引用列（须重开方案）。
3. **可运营**：字段级权限（必须后端大步）。
4. **可协作**：@提及、会话历史列表；审批建议复用 Cube，而非复刻飞书工作流画布。

**建议路线**

1. **立刻可做**：查询收口 OSC（退役 SearchDrawer + SearchData 强制并入 viewFilter）。
2. **后端小步**：延续 e483 口径的 PATCH/批量/提及通知；图表覆盖靠实体配置而非新协议。
3. **后端大步**：字段级权限（GetPage 按用户裁剪，写入/导出对称）。
4. **明确不做或放样例**：画布编排运行时、双向链接写回、对外收集表单、用 ViewProfile 当数据权限；FlowGram 仅设计器（OSC-0010）。

**不要追齐的竞品能力**：云端实时协同编辑、链接分享到互联网、插件市场、钉钉待办/审批生态绑定、按月自动化次数套餐。这些要么与自有数据模型冲突，要么是对方商业壁垒，不是皮肤的职责。

**一句话定位（2026-08-29 / v1.5.1）**：ArcoVue 是吸收多维表交互的 .NET 企业中后台元数据皮肤——领先在树表、删除触发自动化、权限内 Widget/工作台与 ViewProfile；缺口清单经代码复核后，开放 P0 主要只剩**查询收口**，勿再写「筛选只滤当前页 / 无右冻结 / 无 AI 附件」。
