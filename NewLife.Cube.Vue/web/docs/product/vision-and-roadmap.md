# 愿景与路线图：控制器即 CRUD，AI 驱动前端迭代

> **状态：当前方向。** 人与 AI 在开始任何前端迭代前先读本文；当前代码事实仍以 `core/`、`apps/`、`configs/` 为准。

## 愿景

让后端开发者完成实体控制器、菜单和字段元数据后，前端**立即具备可用的 CRUD 能力**：可进入、可查询、可分页、可新增、可编辑、可删除，并跟随权限、主题和基础交互规范工作。

AI 不是为每个控制器机械生成一套独立页面，而是持续强化这条通路：

```text
控制器 + 菜单 + 字段元数据
  -> 默认 CRUD 页面
  -> 按业务需要覆盖局部 Section
  -> 仅在必要时生成完整业务页面
  -> 将可复用能力回流到默认引擎
```

最终目标是把“从后端能力到可操作前端”的距离压缩到最短，同时不牺牲一致性、可维护性、权限边界和可测试性。

## 北极星与非目标

### 北极星

- 新标准实体控制器不需要手写 Vue 页面，即可得到可靠的 CRUD。
- 业务差异优先以最小覆盖表达，避免复制整个页面。
- AI 可以从需求、控制器、字段元数据和现有规范中选择正确的扩展层级，并完成实现、验证和文档同步。
- 每次局部业务定制都可能沉淀为框架默认能力，后续同类控制器自动受益。

### 非目标

- 不为每个实体生成相互独立、难以维护的 CRUD 页面。
- 不为了视觉差异绕开默认页面、主题、权限或 API 契约。
- 不把尚未验证的需求直接固化进 `core/` 默认行为。
- 不用一次性“大重写”代替渐进覆盖和可验证迭代。

## 产品原则

| 原则             | 对 AI 的要求                                                                  |
| ---------------- | ----------------------------------------------------------------------------- |
| 控制器优先       | 先确认控制器、菜单和字段元数据是否已经足够，不默认新建页面。                  |
| 最小覆盖         | 按“元数据 → Section → 整页 → 框架”递进，命中更小层级即停止。                  |
| 约定优于手工注册 | 尊重菜单动态路由、视图目录和 Section 命名约定，不手写平行路由系统。           |
| 默认能力回流     | 两个及以上业务场景重复出现的能力，应评估回流 `core/views/` 或共享组件。       |
| 真实组件即原型   | 直接在 Vue/Element Plus/Tailwind 真实运行链验证，不维护脱离代码的视觉模拟稿。 |
| 质量不后置       | 权限、加载、空态、错误、主题和测试是完成定义的一部分。                        |
| 文档跟随决策     | 新事实更新 reference，新流程更新 guide，新约束更新 standard，新取舍新增 ADR。 |

## AI 默认决策树

AI 收到页面或功能需求时，必须依序判断：

1. **后端控制器、菜单和字段元数据是否已具备？**
   - 是：先访问默认 CRUD，确认是否已经满足；不要生成 Vue 页面。
   - 否：明确缺失的是后端能力、菜单配置还是前端问题，不能用前端页面掩盖后端契约缺口。
2. **默认 CRUD 只差一个局部区块或字段行为吗？**
   - 是：在 `apps/<app>/src/views/<route>/` 生成 Section 覆盖。
3. **需求是否需要独特的信息架构、连续工作流、复杂可视化或跨实体协调？**
   - 是：生成该路径的完整 `index.vue` 页面，但继续复用请求、主题、权限和基础组件。
4. **需求是否会让多个控制器/应用受益？**
   - 是：先评估升级 `core/views/`、`core/components/` 或元数据契约，并补测试与 ADR。

`Section` 名称、视图路径和路由细节见 [路由与页面发现](../architecture/routing.md)；实际操作见 [新增页面](../guides/add-page.md) 与 [覆盖默认页面区块](../guides/customize-page.md)。

## 路线图

路线图描述优先级，不代表所有项目都必须并行实施。每项启动前先确认当前代码事实，并将已完成内容迁入 architecture/reference，而不是把计划写成现状。

### 阶段 1：守住“控制器即 CRUD”闭环

**目标**：标准实体控制器在无手写页面时稳定完成列表、搜索、新增、编辑、删除、分页、权限和错误反馈。

优先事项：

- 统一列表与表单的字段类型映射和校验行为。
- 扩展字段元数据到常见控件：枚举/LOV、数值、日期时间、文件、图片、JSON、富文本等。
- 为字段转换、默认列表和默认表单建立覆盖矩阵测试。
- 修复默认引擎中的体验或契约缺口，而不是在单个业务页面绕开它。

完成信号：新增标准控制器后，AI 能通过菜单直达、刷新、增改删和权限流程验证默认页面。

### 阶段 2：让业务差异以最小覆盖表达

**目标**：绝大多数业务定制通过 Section 和元数据完成，而非复制默认页面。

优先事项：

- 扩充并稳定 Section 边界，保证搜索、工具栏、表格、表单和页头可独立替换。
- 为常见业务模式沉淀可复用覆盖模板，而非复制某个实体页面。
- 让 AI 能从需求自动选择覆盖层级，并在实现后验证路由、主题和回退行为。

完成信号：相似定制不再产生多份整页 CRUD，覆盖文件小且职责单一。

### 阶段 3：AI 生成完整业务工作区

**目标**：当默认 CRUD 不足时，AI 能生成符合规范的完整页面，而不是脱离框架另起一套。

优先事项：

- 支持仪表盘、审批/编排、跨实体工作流、编辑器等完整页面类型。
- 复用 `request`、认证、菜单、主题、通知、布局与数据组件。
- 为关键业务流建立 E2E 验证与可观察的错误/空态/加载态。

完成信号：完整页面仍遵守同一主题、权限、路由和 API 契约，且不会阻塞默认 CRUD 的演进。

### 阶段 4：持续学习与能力回流

**目标**：AI 的每次迭代都减少下一次工作的决策与样板代码。

优先事项：

- 识别重复的 Section、字段映射和交互模式，提炼为默认能力。
- 对重要选择记录 ADR，对稳定规则更新 standards，对当前事实更新 reference。
- 清理不再使用的覆盖和过期文档，避免旧路径误导 AI。

完成信号：同类需求的实现越来越短，且通过默认能力而非复制粘贴获得一致结果。

## AI 迭代完成定义

每次 AI 迭代完成前，必须能回答：

- 这次改动属于默认 CRUD、Section 覆盖、完整页面还是框架能力回流？为什么？
- 控制器、菜单、字段元数据、路由和权限是否已形成可访问闭环？
- 是否复用了最小可行扩展层，而没有复制整页或新建平行机制？
- 加载、空态、错误、确认、主题和无障碍是否遵守 [UI 规范](../standards/ui-spec.md)？
- 是否执行了与风险匹配的测试/构建检查？
- 是否同步更新了事实、流程、约束或 ADR？

AI 的逐步执行模板见 [AI 迭代工作流](../guides/ai-iteration.md)。
