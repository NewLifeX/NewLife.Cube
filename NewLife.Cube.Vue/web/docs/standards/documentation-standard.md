# 文档维护规范

## 目标

文档必须帮助读者在最短路径内找到一个可执行、可验证且不过期的答案。文档不是代码旁边的备忘录，更不是历史草案的堆放区。

## 一文一责

- 一个事实只能有一个权威文档；其他文档只链接，不复制。
- `product` 说明项目方向和阶段优先级；`architecture` 说明结构与协作；`standards` 写必须遵守的约束；`guides` 写任务步骤；`reference` 记录当前事实；`decisions` 保存取舍；`changes` 保存一次迁移；`archive` 只保存有追溯价值的失效材料。
- 不把提案、待实现方案或 FIXME 写成当前行为。提案留在 issue/ADR；实现后再写入 architecture、guide 或 reference。

## 新建与更新

1. 先确定读者的问题，再选择目录；无法归类时先不要新建文档。
2. 标题写结论或任务，不写模糊名词，例如“新增菜单驱动页面”而不是“页面说明”。
3. 每个操作步骤必须给出真实路径、命令或可观察结果；不要保留伪代码作为唯一依据。
4. 文档涉及运行行为时，标出代码权威位置；文档涉及约束时，标出适用范围和例外。
5. 代码变更同时检查受影响的文档：方向或阶段优先级变化更新 product，入口/目录变化更新 architecture，规则变化更新 standards，流程变化更新 guides，配置/API/组件变化更新 reference，取舍变化新增 ADR。

## 状态与失效处理

- 默认文档状态为“当前”，无需额外标记。
- 尚未落地的内容不要进入当前文档；使用 ADR 的“提案”状态或在 issue 跟踪。
- 文档被新权威内容完全替代且无历史价值：删除。Git 历史足够追溯。
- 文档记录重大迁移、外部兼容性或事故复盘且未来仍可能查询：移入 `archive/<year>/`，首行注明“已归档，不指导新开发”，并链接替代文档。
- 删除或移动文档前，搜索并修正入链，不能留下失效 Markdown 链接。

## 质量门槛

- 不复制代码已经能准确表达的长清单；保留意图、边界、入口和例外。
- 不写无法验证的效果宣称，例如“减少 50% 代码”。
- 不写与当前目录、命令、依赖或 API 不符的通用模板。
- 目录入口 `docs/README.md` 必须能导航到每个当前文档类别。
