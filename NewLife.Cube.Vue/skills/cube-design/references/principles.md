# 心智模型：为什么这样设计

> 本文是方法论的"元文档"——不讲怎么做，讲为什么这样做。执行细节见 [page-types.md](./page-types.md)、[component-decision.md](./component-decision.md)、[interaction-patterns.md](./interaction-patterns.md)、[spec-checklist.md](./spec-checklist.md)。

## 一、本质需求：可预期的一致性

用户要的不是"一个好看的页面"，而是：今天做的页面和明天做的看起来像同一个产品；新增页面时不需要重新决定"间距多大、加载怎么表现、按钮用什么颜色"。

**根因**：不一致不是审美差异，而是每个执行者在每个页面都面临大量*未定义的决策*（间距、加载态、错误提示、圆角、字号……）。每个未定义的决策 = 一个分叉点 = 一次不一致的机会。

**核心原则：把分叉点变成单行道。** 不是"建议这样做"，而是"只能这样做"。规格里每条规则都在消灭一个分叉点。

## 二、两套系统，不加第三套

一个页面要解决两类问题：**组件长什么样**（外观：颜色/圆角/hover/disabled/暗色）与**元素怎么摆**（布局：flex/grid/间距/响应式）。

| 系统         | 负责                                                   | 不需要做的事                      |
| ------------ | ------------------------------------------------------ | --------------------------------- |
| Element Plus | 外观。组件已解决 hover/focus/disabled/loading/暗色适配 | 不用重新定义按钮 hover 态         |
| Tailwind     | 布局。utility 已覆盖 flex/grid/gap/padding/响应式      | 不用写 `.container{display:flex}` |

**连接点**：Tailwind 的颜色/圆角映射到 Element Plus 的 `--el-*` 变量（`@theme { --color-primary: var(--el-color-primary); }`），主题切换时 Tailwind class 自动跟随，零改动。

**为什么不加第三套**：任何自定义 token 层（`--app-*`、`--forge-*`）都是在两套系统间插入翻译层——多一套命名、多一个同步点、多一个"这个值从哪来"的追溯成本。只要 `--el-*` + Tailwind 内置系统能覆盖 100% 需求，就不加。

> **本项目的落地情况**：`@newlifex/cube-vue` 框架已经是"两套系统"的实践者——`core/global.css` 只保留 `--el-*` 语义变量；`core/cube-layout-vars.css` 额外提供 `--cube-layout-*` 命名空间的**布局结构尺寸**（侧边栏宽度、导航高度等），这不是第三套"外观"系统，而是 Tailwind 未覆盖的"结构默认值"，允许存在。详见 [cube-layout 技能](../cube-layout/SKILL.md) 的 Token 规范。项目已删除旧的自定义色彩 token 设计草案；新页面**不要**引入 `--tn`、`--bg`、`--ac` 一类平行色彩变量。

## 三、组件优先级（本项目对原方法论的补充）

原方法论假设"从零构建"，只有 Element Plus 与 Tailwind 两级。本项目是成熟框架，多了一层**已封装的业务组件**，必须排在最前面，否则会出现"重复造轮子"这一新的分叉点：

```
1. 框架已有业务组件（CbTable / CubePager / CubeSearch / LovSelect / DefaultEntity ...）
2. Element Plus 原生组件
3. Tailwind 摆放这些组件
4. 都不满足时才新建业务组件（且需过一遍 spec-checklist）
```

## 四、原型即生产（本项目对原方法论的关键调整）

原方法论面向**无构建步骤的静态 HTML 工具**，需要"HTML + CDN 组件"充当可执行原型，再手工翻译成框架代码。

**本项目已有完整 Vue + Vite 构建链路，不存在"原型"与"生产代码"的鸿沟**——直接在 `apps/{app}/src/views/` 下用 Element Plus + Tailwind 写 `.vue` 组件，跑 `pnpm dev` 实时预览，看到的就是最终效果。

> **决策**：跳过"独立 HTML 原型层"，页面开发本身就是原型验收环节。
> **理由**：静态 HTML 原型的价值是"消灭翻译环节的偏差"；本项目从第一行代码起就是真实组件 + 真实构建，不存在翻译环节，再加一层 HTML 原型反而是新增的翻译成本。
> **准则**：只有当需要脱离登录态、脱离路由权限、快速展示多个视觉方案供决策者选择时，才在 `docs/prototypes/*.html`（Element Plus + Tailwind CDN，只读静态文件，不进构建）临时搭一个对比稿；方案定稿后立刻删除，不作为长期资产。

## 五、决策即准则

每次认真做出的设计决策，都要沉淀为可复用的准则，写入 [`web/docs/decisions/`](../../../web/docs/decisions/) 下的 ADR：

```
决策：[做了什么选择]
背景：[面对什么问题/分叉]
理由：[为什么选 A 不选 B]
准则：[抽象为可复用的一句话规则]
```

后续遇到类似分叉时，不再是"决策"（需要思考），而是"选择"（查准则库）。

## 六、spec 的演进机制

- **触发**：执行者遇到 spec 未覆盖的决策点，**不做主观判断**，标记为"spec 缺口"。
- **处理**：负责人做决策并给出理由 → 写入 `docs/decisions/` ADR 与 `docs/standards/ui-spec.md` 对应规则 → 若揭示了新的"为什么"，同步更新本文件 → 已有页面不回溯（除非明确要求），新页面起执行新规则。
- **防膨胀**：单个维度规则超过 10 条时，抽象为"模式"而非逐条列举；规则密度与团队规模正相关；每条规则必须能回答"不定义会怎样"。

## 七、常见陷阱

| 陷阱                 | 说明                                                                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 把设计系统做成组件库 | 设计系统是"告诉你什么场景只能用什么"，组件库是菜单，设计系统是套餐                                                                                               |
| 允许"特殊情况"       | "这个页面比较特殊，间距用 18px 吧"——一旦开口子，每个页面都特殊。除非改 spec，否则不允许例外                                                                      |
| 自定义 token 层      | "Element Plus 没有间距变量，加一套 `--app-space-*`"——两套间距，哪个为准？答案：不需要，Tailwind `p-4` 就是 16px                                                  |
| 主题和组件耦合       | 组件里写死 `#161B22`，换主题时不会变。正确：`bg-bg-page` 映射 `var(--el-bg-color-page)`                                                                          |
| 栅格系统重复         | 页面级布局已用 Tailwind grid/flex，又在同一层级引入 `el-row`/`el-col` 做栅格——两套栅格并存。规则见 [component-decision.md](./component-decision.md) 的"布局边界" |

## 八、判断 spec 是否够用

把 `docs/standards/ui-spec.md` 和一个新页面需求交给不了解项目的人（或 AI）：
- 产出"和现有页面看起来像同一个产品" → spec 够了
- "结构对但细节不同" → 有维度没覆盖，补充 spec
- "完全不像" → spec 太抽象，需要加具体代码示例

## 九、适用范围

适用：多人协作或 AI 辅助产出页面、需要快速产出一致 UI、有共享基础设施（框架组件/主题变量）的产品。
不适用：营销页/落地页（需要大量自定义视觉）、纯设计探索阶段（还在找方向，不适合固化规则）。
