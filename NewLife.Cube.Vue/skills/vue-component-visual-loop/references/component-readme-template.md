# 组件 README 模板（component-readme-template）

> 本文件是 `vue-component-visual-loop` 技能 §七 的完整模板。每个组件目录（`core/components/<Name>/`）都应有一份 `README.md`，作为「设计 ↔ 功能 ↔ Story ↔ 测试 ↔ 验证」的**唯一事实源**。
>
> **Part A 为开发前必填**：开始编码前必须产出并经评审，它是验收标准与后续验证的输入。
> **Part B 为开发中 / 后沉淀**：随「改代码 → 逻辑回归 → 视觉预览 → 截图锁定」闭环逐步补全。

---

## Part A：开发前必填（动手前产出，建议评审）

### 1. 功能需求（Functional Requirements）
> 用什么角色、要做什么、达到什么结果。每条必须可验收（能被测试或人肉确认）。
- **FR1**：作为 `<角色>`，我希望 `<功能>`，以便 `<价值>`。验收：`<可观察的结果>`。
- **FR2**：……
- （交互类补充：支持单选 / 多选、搜索、分页、清空、回填、禁用态吗？）

### 2. 设计（Design）
- **定位**：一句话说明干什么、被谁用、何时出现（弹窗 / 内联 / 独立页）。
- **分层 / 契约**：UI 薄壳 + 逻辑层（`*.logic.ts` 纯函数 或 `use*.ts` Hook）；自身不 `fetch` 什么、调用方须先准备什么（props / 注入）。
- **交互模式**：如「多选=复选框且跨页 reserve；单选=radio 选中即关闭」「搜索防抖 300ms」「键盘可达性」。
- **视觉要点**：布局、密度、主题变量、空 / 加载 / 错误态外观。

### 3. 流程（Flow）
- **用户操作流程**：从打开到完成的主路径 + 关键分支（如翻页后已选是否保留、搜索后是否重置页码）。
- **关键数据流**：props 入 → 内部状态 → emits 出；涉及的后端请求时机与依赖。
- **状态机**（如有）：如 `closed → open → selecting → confirmed`，标注每态可见 UI 与可触发事件。

### 4. 功能验证列表（Verification Checklist）
> **源于 §1 功能需求**，逐条可勾选，是"开发完成"的验收清单，也是 §10 类人验证的输入。
| # | 验证项（源于 FR） | 前置状态 | 操作步骤（`?story=` 深链打开后） | 期望结果 | 状态 |
|---|---|---|---|---|---|
| V1 | … | … | 点击… / 翻到第 N 页… | 文字 / 勾选数… | ☐ |

### 5. 数据契约（Data Contract）
- **依赖接口**：组件依赖的后端接口 / 数据源（路径、方法、关键字段）。
- **字段与枚举映射**：展示值 ↔ 原始值映射（如 `status: 1→启用`）；字典来源（接口 meta / 本地常量）。
- **Mock 约定**：Vitest / CT 下如何提供数据（Vite 别名 mock、fixture），**确保不请求真实后端**——
  组件内部凡涉及被 mock 的模块必须用项目别名导入，不能用相对路径（相对路径会绕过别名桩，在 Gallery / CT 里打到真实后端，导致组件空白或返回原始值）。

### 6. 边界与异常（Edge cases）
- 空数据、加载中、错误态、超大列表（虚拟滚动？）、超长文本截断、分页边界（最后一页单行）、连续快速操作、禁用态。

### 7. 待确认项（Open Questions）
> 开发前必须清零或显式记录。未决事项不要带进编码。
- [ ] ……

## Part B：开发中 / 后沉淀（闭环产出）

### 8. 功能 ↔ Story ↔ 测试 对应表
Vitest 覆盖逻辑层（`<Name>.spec.ts`）；CT 覆盖 UI 渲染与交互（`<Name>.ct.spec.ts`）。
每个 story 在 `<Name>.story.ts` 内用「测试状态：」注释标明验证的运行时状态。
| 功能 | Story（`<Name>.story.ts`） | Vitest（`<Name>.spec.ts`） | CT（`<Name>.ct.spec.ts`） |
|---|---|---|---|
| F1 … | `<Name>/Xxx` | 覆盖（…） | `用例名` |

### 9. 视觉基线说明（Visual Baselines）
- 需要锁定像素基线的关键状态（如弹窗打开、某分页、某选中态），命名与 story 对应。
- 基线更新需人工 review（详见技能 §六 CI 与基线管理），避免无意识覆盖。

### 10. 验证流程（类人点击验证）
启动 `ct:server` 后，按技能「类人点击验证流程」（§八）逐项点击 / 翻页 / 断言文字与勾选数，等价于真人在浏览器逐一确认功能真的可用。截图统一输出固定目录 `ct/verify-shots/`（与 `ct/` 同目录，瞬态产物）。**复用 §4 验证列表作为操作清单**，每完成一项勾选并截图核对。

## 运行测试
```bash
pnpm test:unit                                   # Vitest 全部
pnpm exec vitest run --config vitest.config.unit.ts <Name>   # 单文件
pnpm test:ct:update    # CT 刷新基线   pnpm test:ct  # 回归对比
```

> 该 README 让"改代码→看 Vitest→按 Story 看视觉→CT 锁基线"的导航图始终成立，并把"人肉确认"固化为可复跑的验证清单（§4 + §10）。
