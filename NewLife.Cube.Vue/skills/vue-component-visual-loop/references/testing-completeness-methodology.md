# 测试完备性方法论（组件开发理论指导）

> 本文件是 `vue-component-visual-loop` 技能 §十 的深度展开。它把"组件测试怎么写才不漏功能、不假绿"沉淀为可复用的成熟理论，让下次开发组件时：**先写 README（按理论不漏功能）→ 派测试（覆盖会出问题的地方）→ 实现（红转绿、调试有路径）→ 最后按故事逐一走查通过**。

---

## 0. 要解决的两类失败

组件开发中最常见的两类"看起来完成了、其实没完成"：

| 失败类型 | 表现 | 典型后果 |
|---|---|---|
| **漏功能** | 开发完发现某形态 / 某状态没做（只做单选忘多选、列表回显显示数字、禁用态没处理） | 用户报 bug、返工 |
| **假绿** | 所有自动化测试全绿，但线上有缺陷 | 截图只锁视觉不锁语义；mock 把缺陷也一起 mock 掉了 |

本方法论用 **README 三块理论载体 + 四阶段流程**，从根上消除这两类失败。

---

## 1. 理论根基（成熟框架，非自创）

这些都是业界已有定论的实践，按本组件场景落地即可，不必重新发明。

| 框架 | 提出 / 代表 | 一句要义 | 在本方法论的落点 |
|---|---|---|---|
| **TDD（Red-Green-Refactor）** | Kent Beck | 先写会失败的测试，再实现让其转绿，最后重构 | Phase 2：测试先于 / 伴随实现；动手前先确认测试"能红" |
| **BDD / Specification by Example** | Dan North / Gojko Adzic | 需求 = 可执行的例子；Given-When-Then 描述验收 | FR + 故事 + 验收标准（§2.3） |
| **测试金字塔** | Mike Cohn | 多单测、少集成、更少 e2e | 单测（逻辑层）+ CT（交互层）+ 类人验证（轻 e2e）三层分工 |
| **特征测试 Characterization tests** | Michael Feathers | 改未知 / 遗留行为前，先锁住当前行为 | 改前先截图 / 断言锁当前表现，再动 |
| **契约测试 Consumer-Driven Contracts** | Pact 等 | 消费者与生产者的接口契约独立验证 | lovStore 这类被 mock 的模块，必须有"真实模块契约测试" |
| **测试替身忠实性 Test Double Fidelity** | xUnit 测试模式 | mock 行为必须匹配真实，否则测的是假象 | CT 桩必须写"忠实性测试"，防止桩悄悄作弊 |
| **变异意识 Mutation-aware** | 行业实践 | 测试必须能失败，否则毫无价值 | 每个不变量守卫测试，先确认它"因正确原因变红" |
| **每缺陷一回归测试** | 行业实践 | 每个 bug 都要有复现 / 守护测试 | 不变量表 + 反向命名回归用例（"不应是数字"） |

## 2. README 三大理论载体（防漏 + 防假绿）

开发前 README 必须含以下三块。它们是"理论"在文档上的具体落点——**少一块，就会出现对应的失败类型**。

### 2.1 能力维度矩阵（Completeness Matrix）—— 防漏功能

> 漏功能的本质：需求是平铺的 FR 列表，人脑会无意识地跳过某些"组合"。

做法：枚举所有"会变"的维度，画成矩阵。**每个可达的单元格 = 一个必须实现且必须测试的能力**；空白单元格 = 要么明确标注"不支持"，要么就是漏了。

常用维度（按组件取用，不必全列）：

| 维度 | 取值示例 |
|---|---|
| 形态 | 单选 / 多选 |
| 来源类型 | ENUM / LIST（列表弹窗）/ 远程搜索 / 本地常量 |
| 值状态 | 空值 / 部分选中 / 全选 |
| 组件态 | 只读 / 可编辑 / 禁用 |
| 数据态 | 无网络 / 加载中 / 出错 / 空结果 / 大量数据（分页） |
| 交互 | 打开 / 选择 / 取消 / 确认 / 删除已选 / 搜索 / 清空 / 翻页 |

矩阵示例（LovSelect 节选）：

| 形态＼来源 | ENUM | LIST |
|---|---|---|
| 单选 | 单选下拉 + 回显 label ✅ | 只读 input + 搜索图标开弹窗 + 回显文本 ✅ |
| 多选 | 多选 + collapse-tags ✅ | 只读 + 弹窗多选 + 回显文本（非数字）✅ |

> 这张矩阵一眼就能看出"LIST 多选回显"是否覆盖——本会话正是这一格曾经破（显示数字），被补进不变量 INV-1。

### 2.2 不变量红线（Invariants）—— 防假绿

> 假绿的本质：测试只在"正常路径"上绿，从不断言"绝不允许发生什么"。

做法：开发前就列出"**容易破、破了用户立刻可见**"的红线，每条写清"为什么容易破 / 破了后果"。不变量是**负向约束**（expect 绝不允许…），必须有一条守卫断言测试（见 §3）。

不变量模板：

```
| ID | 不变量（负向约束） | 为什么容易破 / 破了后果 | 守卫测试 |
```

> 例（LovSelect INV-1）：LIST 回显必须显示文本 label，绝不允许回退成原始数字 id。
> 为什么容易破：`confirmMulti` 只 emit 纯 id、`loadMeta` 漏消费 inlineEnums 都会让 `getSelectedLabel` 查不到 label → 回退数字。破了后果：用户无法识别已选。

### 2.3 故事清单（Stories / 验证表）—— 最终走查闸门

> 交付的本质：不是"代码写完"，而是"每个故事都验证通过"。

做法：README §4 验证列表即故事清单。每个故事 = 一个 `?story=` 深链 + 操作步骤 + 期望结果。**开发完成后按此逐项走查，全部 PASS 才算完成**——这就是用户要的"按故事一一测试并通过，而不是这也漏那也缺"。

## 3. 四阶段开发流程（对齐用户期望）

```
Phase 0  写 README（矩阵 + 不变量 + 故事）
         └─ 评审：矩阵无空白格、不变量覆盖了"会出问题的地方"、故事可勾选
              ↓
Phase 1  派测试（从文档生成，而非从代码猜）
         ├─ 从故事 → CT 语义断言（toContainText，不只截图）
         ├─ 从不变量 → 守卫断言测试
         └─ 凡 mock 掉的核心逻辑 → 额外生成「真实契约测试 + 桩忠实性测试」双测
              ↓
Phase 2  实现（让测试从红转绿，调试有清晰路径）
         ├─ 逻辑抽到 *.logic.ts / use*.ts（关注点分离，便于单测）
         ├─ 组件内被 mock 的模块用项目别名导入
         └─ 先确认测试"能因正确原因变红"，再实现转绿
              ↓
Phase 3  故事走查闸门（按 §4 逐项 PASS/FAIL）
         └─ 全 PASS → 交付；任一 FAIL → 回到 Phase 2
```

**为什么这个顺序能"很快调试完成"**：因为每个故事 / 不变量都有对应测试，改一处行为，对应测试立刻红——定位路径极短，不必全量人肉点。

## 4. 防假绿纪律（本会话真实教训）

本会话 LovSelect 曾出现真实缺陷「LIST 多选 / 单选关闭态回显数字而非文本」，修复前**所有自动化测试全绿**。复盘出四层叠加原因，沉淀为纪律：

1. **CT 桩不忠实（最致命）**：旧 CT 桩 `getSelectedLabel` 带"按 id 回退源数据"作弊，把数字 `1` 伪装成 `管理员` → 缺陷被桩抹平。
   → 纪律：CT 桩必须忠实；并对桩本身写「忠实性测试」。
2. **只有截图、没有语义断言**：截图锁"视觉长相"不锁"语义对错"；且基线若在缺陷态捕获，会**固化 bug**。
   → 纪律：凡用户可见文本必用 `toContainText` 断言；绝不在缺陷态更新截图基线。
3. **单测把核心逻辑整个 mock 掉**：`vi.mock('./lovStore')` 把 `getSelectedLabel` 桩成 `label-${v}`，逻辑层从未走真实解析路径。
   → 纪律：mock 掉的核心模块，必须另设"真实模块契约测试"覆盖其被 mock 掉的逻辑。
4. **缺"回显必须是文本而非数字"的断言**：ENUM 有同类断言，LIST 没有。
   → 纪律：不变量每条都要有守卫测试，写入"不变量 ↔ 测试"映射表。

**双测保险公式**（mock 掉核心逻辑时必做）：

```
真实模块契约测试（lovStore.test.ts）  +  桩忠实性测试（mockFidelity.spec.ts）
                 ↓ 二者缺一，缺陷就会被 mock 掩盖
```

**测试须先确认"能因正确原因变红"**：本会话曾写出"变红于错误原因"的测试（选择器写错，报元素找不到而非"显示数字"），需修正选择器。变红≠有效，必须红在正确断言上。

## 5. 真实案例（LovSelect LIST 回显数字）

完整复盘见 `core/components/LovSelect/README.md` Part C §13–§16。一句话总结：
- 缺陷：多选确认 / 单选关闭态回显显示 `1`/`2`，用户无法识别已选。
- 为何没被测试抓到：上面 §4 四层原因全部命中。
- 修复后补的测试（即本方法论的落地）：
  - `ListMulti 选择后回显文本(不应是数字)`、`ListSingleEcho 回显文本(不应是数字)`（CT 语义断言，守护 INV-1）
  - `lovStore.test.ts`（真实模块契约，守护 INV-5）
  - `LovSelect.mockFidelity.spec.ts`（CT 桩忠实性，守护 INV-6）

## 6. 一份"不漏功能"的 README 自检清单

写 / 评审 README 时逐项勾：

- [ ] **能力维度矩阵**已画，无未说明的空白格（漏功能检测）
- [ ] 矩阵每个"支持"格都有对应 FR 与故事
- [ ] **不变量红线**已列，每条标注"为什么容易破"
- [ ] 每个不变量都有守卫测试（在"不变量 ↔ 测试"映射表）
- [ ] **故事清单（§4）**每条可勾选，有 `?story=` 深链 + 操作步骤 + 期望
- [ ] 凡用户可见文本，测试用 `toContainText` 断言（不止截图）
- [ ] mock 掉的核心逻辑，有「真实契约测试 + 桩忠实性测试」双测
- [ ] 截图基线**未**在缺陷态捕获 / 更新

> 这六条全勾，基本可保证"开发组件不会漏功能、测试能测出问题、最后按故事逐一通过"。
