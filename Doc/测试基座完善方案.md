# NewLife.Cube 测试基座完善方案

> 状态：待评审 | 编制依据：仓库现状调研（2026-08-23）+ 家庭组功能实施复盘
> 本方案只描述计划，不含任何已执行的改动。

---

## 一、现状快照

### 1.1 测试资产盘点

| 项目 | 性质 | 基座方式 | 纳入解决方案 | 备注 |
|---|---|---|---|---|
| `NewLife.Cube.Tests` | 服务层集成测试（9 个文件） | 手工 `DefaultHttpContext` + 真实 `UserService`/`ManageProvider2` + SQLite 集合夹具 | ✅ 两个 sln 均含 | 不起 Web 主机 |
| `XUnitTest` | 纯单元测试（42 个文件） | 静态/内存测试，无宿主 | ✅ 两个 sln 均含 | 引用了 `Microsoft.AspNetCore.Mvc.Testing` 但**未使用**；另引用 `NewLife.MySql`、coverlet |
| `E2EMvcTest` | Playwright 端到端（10 个文件） | 启动真实 CubeSSO 进程 + SQLite 临时库 + Chromium headless | ✅ 两个 sln 均含 | 依赖本机浏览器环境 |
| `Test` | 控制台 Exe | 手工调试用，非自动化测试 | ❌ 不在任何 sln | 疑似废弃 |
| 家庭组测试（本次新增） | 业务单元 + API 集成 | `CustomWebApplicationFactory` + 真实 HTTP 管道 + SQLite | ✅（随其所在工程） | 每个测试构造函数调 `ResetDatabase()` |

### 1.2 CI 现状

- `test.yml`：所有分支 push/PR 时执行 `dotnet test 魔方.sln`（全解决方案，含 E2E 项目）。
- `publish.yml`（tag）与 `publish-beta.yml`（master）：**只构建打包，不跑测试** —— 存在"发布物未经测试门禁"的缺口。
- 前端测试脚本（`test:unit`/`test:e2e` 等）存在但未接入 CI。

### 1.3 关键技术事实

1. 主项目多目标框架 `net6.0~net10.0`，所有测试项目仅 `net10.0`。
2. 仓库中**没有任何 `xunit.runner.json`**，并行策略完全依赖各测试类上的 `[CollectionDefinition(DisableParallelization=true)]` 声明。
3. `NewLife.Cube.Tests` 的 `TenantAuthFixture` 通过反射注入 `ManageProvider2.Context`（internal static），代码注释和《多租户改造验证清单》均已建议用 `InternalsVisibleTo` 替代。
4. `OAuthLogRetentionTests` 不在任何串行集合内，却调用 `DAL.AddConnStr("Cube", ...)` 覆写全局连接串；xUnit 默认跨集合并行，与 `TenantAuth` 集合的 `MapTo` 映射存在理论竞争。
5. 家庭组实施的教训（已验证）：真 HTTP 管道会引入 JWT 中间件校验、HostedService 冲突、`HTTP 200 + code=-1`、XCode 启动建表噪声四类固有问题；逐测试 `ResetDatabase()` 清表在并行下互相破坏，最终靠并入串行集合解决。

## 二、问题清单（按风险排序）

| # | 问题 | 影响 | 证据 |
|---|---|---|---|
| P1 | 发布流水线无测试门禁 | 回归可随发布流出 | `publish.yml`/`publish-beta.yml` 无 test 步骤 |
| P2 | 全局状态类测试的并行隔离只靠分散的 `[Collection]` 声明，无全局兜底 | 新增测试类若忘记声明集合即可能互踩（`OAuthLogRetentionTests` 已是既成隐患） | 无 `xunit.runner.json`；该测试覆写全局 `DAL` 连接串 |
| P3 | 集成测试基座分裂：`TenantAuthFixture`（服务层直调）与家庭组 `CustomWebApplicationFactory`（真管道）并存，数据策略互不兼容（种子一次不清表 vs 逐测试清表） | 新测试无标准可依，重复踩坑 | 本次实施的 5 类故障复盘 |
| P4 | 反射注入 `internal static` 成员 | 重构易碎、可读性差 | `TenantAuthReproTests.cs:105-107` |
| P5 | `Test\` 废弃工程残留；`XUnitTest` 冗余包引用 | 认知负担、构建噪声 | 调研结论 |
| P6 | `dotnet test 魔方.sln` 会连带运行 E2E（Playwright）项目，依赖浏览器运行时 | PR 流水线在缺浏览器环境的 runner 上可能失败或不稳定 | `E2EMvcTest` 在 sln 内 |

## 三、改进方案（三阶段）

### 阶段一：门禁与运行配置（低风险，立即可做）

**1. 发布流水线加测试门禁**
- 改动：`publish.yml`、`publish-beta.yml` 在 pack 之前复用 `test.yml` 的测试步骤（抽取为可复用 workflow 或直接内联 `dotnet test`）。
- 验证：手动触发一次 beta 发布，确认测试失败时发布被阻断。

**2. 为 `NewLife.Cube.Tests` 增加 `xunit.runner.json`**
- 内容：`parallelizeTestCollections = false`。理由：该工程 9 个文件全是全局状态敏感测试（DAL 连接串、`ManageProvider`、`CubeSetting`），集合级并行收益≈0、风险>0。`XUnitTest` 为纯单元测试，保持默认并行不动。
- 验证：跑一次全量测试确认通过；`OAuthLogRetentionTests` 无需再单独收编（全局兜底已覆盖）。

**3. 拆分 E2E 出 PR 默认路径**
- 改动：给 `E2EMvcTest` 的测试类加 `[Trait("Category","E2E")]`，`test.yml` 用 `--filter Category!=E2E` 跑快车道；新增 `e2e.yml`（或 job）在 push 到 master/定时任务中跑全量含 E2E。
- 验证：PR 流水线不再拉起 Chromium；master 流水线 E2E 全绿。

**4. 清理已知噪声项（可并入上面任一次提交）**
- 家庭组测试中 JWT 编码处的 nullable 警告；
- 测试主机的 HTTPS 重定向提示（在 `CustomWebApplicationFactory` 中显式关闭重定向中间件或配置 HTTPS 端口）；
- `WeChatTemplateHelperTests` 的 xUnit 断言风格警告。

### 阶段二：集成测试基座统一（核心）

**5. 确立两层集成测试的分工标准**（写进 `Doc` 或测试工程 README，约束后续新测试）

| 层 | 适用 | 基座 | 断言 |
|---|---|---|---|
| 服务层集成测试 | 领域逻辑、登录/租户语义、数据权限 | `TenantAuthFixture` 式：手工 HttpContext + 真实 Service | `ServiceResult` + 库内记录 |
| API 端到端测试 | 路由、过滤器、`ControllerBaseX` 鉴权、`ApiResponse` 包装 | `CustomWebApplicationFactory` 式：真实 HTTP 管道 | 反序列化 `ApiResponse<T>`，禁止只断言 `IsSuccessStatusCode` |

**6. 去反射：主程序集加测试接缝**
- 改动：`NewLife.Cube.csproj` 增加 `InternalsVisibleTo("NewLife.Cube.Tests")`；`TenantAuthFixture` 删除反射注入，直接赋值 `ManageProvider2.Context`。
- 前置：按仓库约定，改动 `ManageProvider2` 相关符号前先做影响面分析。
- 验证：`TenantAuth` 集合全绿。

**7. 夹具下沉为共享测试基础设施**
- 改动：在 `NewLife.Cube.Tests` 内建 `TestKit/` 目录，放入 `TenantAuthFixture`、`TestCacheProvider`、`CreateContext` 帮助方法与"进程级状态契约"注释（哪些静态状态会被改、谁负责恢复）。
- 收益：家庭组后续若补服务层测试可直接复用，不再各写一套。

**8. 数据策略迁移：废掉逐测试 `ResetDatabase()`**
- 目标模式（二选一，按场景）：
  - **种子一次 + 唯一键隔离**（默认）：集合夹具建库一次、种子一次，测试内用自增/`Guid` 生成唯一用户名/组名避免冲突。参照 `TenantChecklistIntegrationTests.NewUser()`。
  - **每测试独立临时库**（需要干净表的少数场景）：`Guid` 命名的临时 SQLite 文件 + `DAL.CreateTable()`，参照 `OAuthLogRetentionTests`。
- 家庭组测试迁移：`ResetDatabase()` 从构造函数移除，改为集合夹具建库一次 + 唯一键；保留串行集合作为兜底。
- 风险点：迁移过程可能暴露依赖"清表副作用"的用例，需逐个确认断言自足。

**9. 统一 `ApiResponse` 断言帮助器**
- 提供 `AssertApiResponse<T>` 扩展：同时断言非空、`code`、`Data`；失败场景显式断言 `Data==false` 或业务错误码。杜绝"只查 200"的回归盲区。

### 阶段三：清理与覆盖治理

**10. 清理冗余**
- `Test\` 工程：确认后从仓库移除或移入归档目录（破坏性操作，需单独确认）。
- `XUnitTest`：核实并移除未使用的 `Microsoft.AspNetCore.Mvc.Testing`、`NewLife.MySql` 包引用。

**11. 覆盖率接入 CI（只报告不门禁）**
- `XUnitTest` 已含 coverlet：`test.yml` 增加 `--collect:"XPlat Code Coverage"` 并在 PR 中输出摘要；先不设阈值门禁，避免初期误伤。

**12. 多目标框架策略（明确"不做"）**
- 测试保持 `net10.0` 单目标。主项目虽多目标，但测试矩阵按最新 TFM 跑是当前合理取舍；若未来出现低版本兼容缺陷，再按症状补对应 TFM，不预先铺开。

**13. 前端测试接入（记录在案，本期不实施）**
- `test:unit`/`test:playwright` 等脚本已存在但未进 CI；属于前端工程自治范围，建议由前端同学评估后单独接入。

## 四、明确不做的事

1. 不为测试引入真实 MySQL/Redis —— 全部用 SQLite + 内存缓存替代（与现有夹具一致）。
2. 不把服务层集成测试升级为真 HTTP 管道测试 —— 两层分工各有价值（本次复盘：真管道的四类固有问题不值得在已有覆盖上重复付出）。
3. 不扩大测试的目标框架矩阵（见 12）。

## 六、执行顺序与依赖

```
阶段一（1→2→3→4）彼此独立，可任意顺序、分批提交；
阶段二依赖阶段一完成（串行兜底就位后再做数据策略迁移）；
步骤 8 依赖步骤 7（夹具下沉后才好迁移家庭组测试）；
阶段三全部为独立清理项。
```

每步完成后运行 `dotnet test 魔方.sln --filter Category!=E2E` 作为回归基线。
