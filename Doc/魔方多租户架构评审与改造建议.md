## 一、总体评价

这两次提交把魔方多租户从"能用"推向了"安全"，方向完全正确，有几个值得肯定的设计：

1. **纵深防御（defense-in-depth）**：数据隔离做了四层——中间件（DataScopeMiddleware）、认证层（ValidateTenant/TryLogin）、控制器层（CreateWhere/Valid）、ORM 层（TenantInterceptor + WhereBuilder）。任意单层被绕过都有下一层兜底。
2. **fail-closed 数据查询**：无租户上下文或租户无效时拼 `1=0` 返回空集，而不是静默全量。这是行业里很多框架都做反了的地方（常见错误是"没拿到租户就不过滤"），魔方做对了。
3. **AsyncLocal 生命周期修复**：DataScopeMiddleware 进入时保存旧上下文、`finally` 无条件恢复，杜绝了线程池复用导致的租户上下文跨请求泄漏——这是静态 AsyncLocal 方案最经典的事故来源。
4. **安全加固成体系**：租户 Cookie HttpOnly、登录/注册入口补建 TenantUser、菜单树接口过滤、微信登录 appId 一致性校验、租户切换入口权限收敛，覆盖面完整。
5. **X-Tenant 传 Code、X-Tenant-Id 传数字 ID 的语义约定**清晰，且纯数字编码不会被误判为 ID，避免了枚举攻击面。

但从行业成熟方案的标准看，当前实现仍有 **2 个 P0 级问题、4 个 P1 级结构问题**，以及若干可优化点。

## 二、问题清单

### P0-1　GetTenantId 空 Cookie 引发 NullReferenceException（登录入口级故障）

`ManagerProviderHelper.GetTenantId` 第 740 行：

```csharp
var key = $"TenantId-{SysConfig.Current.Name}";
return ResolveTenantById(req.Cookies[key].ToString());   // Cookie 不存在时 NRE
```

前面三个来源（Header/Query）都做了 `IsNullOrEmpty` 判空，唯独最后的 Cookie 分支没有。`IRequestCookieCollection[key]` 对不存在的 key 返回 null，`.ToString()` 直接抛 NRE。

**根因单点、触发点四处**（均已用测试复现）：

1. `DataScopeMiddleware → GetTenantId`——最早的触发点，无 Cookie 请求在中间件即 500，连控制器都到不了；
2. `UserService.CompleteLogin → EnsureTenantUser → GetTenantId`——**真实 API 登录管线直接异常**：`LoginByPassword` 先经 `ManageProvider2.Login` 预颁发令牌，随后 `CompleteLogin` 内 `EnsureTenantUser(474)` 即命中 NRE，登录请求 500，客户端拿不到任何令牌，且预颁发的令牌记录残留为孤儿（见 P2-10）；
3. `TryLogin → ValidateTenant → ChooseTenant → GetTenantId`——令牌后续请求被拒；
4. 令牌颁发成功之后：即使登录带 Cookie 得以完成（或 P0-1 修复后），无绑定用户的后续请求仍因 `ChooseTenant` 无法落位、`ValidateTenant` fail-closed 而被拒（401）——"令牌已发但不可用"，见复现测试 `Repro_LegacyUser_LockedOut_When_Tenant_Enabled_Without_XTenant`。

影响面：**所有不带 Cookie 的请求**（纯 API 客户端、小程序、首次访问、登录请求本身）在多租户开启后全部命中异常，表现为 500。复现测试 `Repro_GetTenantId_Throws_Without_Cookie`（根因最小复现）与 `Repro_RealLoginPipeline_Throws_Before_Token_Response`（真实管线）。

由此得出修复要求：**只修某一处调用点（例如只在中间件兜底）不够**，必须修 GetTenantId 本身。修复只需一行（判空返回 -1，语义"未提供租户"）：

```csharp
var str = req.Cookies[key];
return str.IsNullOrEmpty() ? -1 : ResolveTenantById(str);
```

另注意一个次生问题：真实登录管线中该 NRE 会被 `LoginByPassword` 的 catch 当作登录失败计入风控（`HandleLoginError` 累加错误次数），无租户信息的正常请求会污染错误计数，可能提前触发"登录错误过多"锁定。

### P0-2　存量用户锁死：开启多租户没有迁移路径

这是本次改造最大的产品级缺陷。`EnableTenant` 从 false 切到 true 的瞬间：

- 所有存量普通用户没有任何 `TenantUser` 绑定；
- `ChooseTenant` 对无绑定的普通用户"不设置租户上下文"（防越权，逻辑本身没错）；
- `ValidateTenant` fail-closed，`TenantContext.CurrentId == 0` → 拒绝。

需要澄清的一点：`EnsureTenantUser` 并非只在注册路径触发——它在 **所有登录路径** 都会经 `UserService.CompleteLogin`（第 474 行）调用。但它内部 `tenantId <= 0 || userId <= 0` 时直接 return：请求不携带任何租户信息（无 X-Tenant/Cookie）时解析不出租户，补建不发生；且解析过程还会先命中 P0-1 的 NRE。

结果：除系统管理员外，**全部存量用户被一次性锁死**。自救通道只有一条——**重新登录并携带有效 X-Tenant**，由 EnsureTenantUser 补建绑定（已有绿色测试 `LegacyUser_Can_SelfRecover_By_Relogin_With_XTenant` 验证）；但令牌认证路径不补建绑定，**旧令牌即使携带 X-Tenant 也无法自救**（复现测试 `Repro_LegacyUser_OldToken_Rejected_Even_With_XTenant`），且典型客户端根本不知道也不应该必须传租户编码。

行业里任何"给存量单租户系统加多租户"的改造，都必须配套**默认租户迁移策略**，这是必选项而非可选项（见第四节改造方案第 4 条）。

### P1-3　租户校验逻辑五处分散，错误语义互不一致

同一件事——"当前用户是否有权处于当前租户"——被实现了至少五次：

| 位置 | 行为 | 失败表现 |
|------|------|----------|
| DataScopeMiddleware | 校验 TenantUser 归属 | 403 文本 / 400 文本 |
| ValidateTenant（TryLogin/Auth） | ChooseTenant 后检查 CurrentId | 401「登录超时」 |
| ControllerBaseX token 路径 | 再次 ValidateTenant | 403 ApiException |
| CreateWhere | 无上下文/无效租户 | 静默 `1=0` 空集 |
| ReadOnlyEntityController2.Valid | 写路径归属校验 | NoPermissionException |

同一个"无租户权限"，客户端可能收到 500（NRE）、401、403、400 或"空数据"五种截然不同的结果。后果：客户端无法统一处理；排障困难；任何一处逻辑调整都要五处同步，极易漏改（本次 NRE 就是 GetTenantId 单点修改未全路径验证的后果）。

### P1-4　租户解析无缓存、认证路径带副作用

- 每个认证请求的链路开销：`GetTenantId`（Tenant.FindById）→ `ChooseTenant`（TenantUser.FindAllByUserId + User.FindByID + Roles 加载）→ DataScopeMiddleware 再来一次 `TenantUser.FindByTenantIdAndUserId`。同一请求内对同样数据 3~5 次 DB 往返，全部无缓存。
- `ChooseTenant` 在认证路径里会调用 `SaveTenant` **写 Cookie**——意味着任意一个已认证的 GET 请求都可能收到 `Set-Cookie`，把租户改写成"第一个有效租户"。认证/解析环节不应有写响应副作用，这让行为难以预测、难以测试。

### P1-5　`TenantId = 0 / null / >0` 三态用魔法数字表达

当前用 `TenantContext.Current == null` 表示"未启用/未设置"、`TenantId == 0` 表示"管理后台"、`>0` 表示租户。`0` 同时承担三种角色：模式标志、校验旁路信号、以及和数据表 TenantId 字段共享的名字（但数据行里永远不应以 0 作为有效租户值）。所有下游都靠"记得 0 是特殊值"来保持一致——CreateWhere 在 0 时不过滤、TenantInterceptor 在 0 时不校验、ChooseTenant 在 0 时只放行管理员。一致性靠约定而非类型系统，是未来回归缺陷的高发区。完整语义盘点见第三章。

### P2-6　静态 AsyncLocal 与 HttpContext 双轨存状态

`TenantContext.Current`（静态 AsyncLocal）与 `HttpContext.Items`（SetTenant 的镜像）两处存同一状态，且静态全局量让单元测试必须手工清理（测试夹具里处处 `TenantContext.Current = null!` 的 finally 就是这种痛感的直接体现）。行业主流做法是 DI scoped 服务（见第四节第 2 条）。

### P2-7　fail-closed 的可用性代价没有对冲手段

`1=0` 静默空集对安全是加分项，但对可用性是减分项：前端只会看到"没有数据"，无法区分"真的没数据"和"租户上下文丢了"。同时管理后台想**显式跨租户查询/报表**也没有正规通道，只能隐式依赖 TenantId=0 不过滤。成熟方案通常把这里做成可配置策略，并提供显式的跨租户 scope（见第四节第 3 条）。

### P2-10　登录令牌重复颁发，产生孤儿且有效的 UserToken（v1.1 新增，已用测试复现）

真实登录管线里 `IssueLoginToken` 会被调用**两次**：

1. `ManageProvider2.Login`（密码校验通过后）颁发一次——插入 UserToken、JWT 缓存进 `Items["jwtToken"]`；
2. `UserService.CompleteLogin` 末尾（第 494 行）再调一次——而 `IssueLoginToken` 并不复用 `Items` 里已有的 JWT，**无条件再插入一条新 UserToken** 并覆盖缓存。

后果：每次成功登录产生两条令牌记录，第一条刷新令牌成为孤儿——从未交付客户端，却保持 `Enable=true` 且 7 天有效期内可用于 `RefreshToken`。一是令牌表持续膨胀（每次登录 +1 条垃圾行）；二是数据库一旦泄露，存在一批从未发出却依然有效的刷新令牌。登录失败路径同样受损：P0-1 的 NRE 中断登录时，预颁发的令牌记录照样残留（复现测试 `Repro_RealLoginPipeline_Throws_Before_Token_Response` 中断言了孤儿存在）。

修复方向二选一：`CompleteLogin` 改为 `if (!context.Items.ContainsKey("jwtToken")) context.IssueLoginToken(...)`；或让 `IssueLoginToken` 幂等（`Items["jwtToken"]` 已存在时直接复用并返回对应 UserToken）。复现测试 `Repro_Login_Issues_Token_Twice`（绿色=缺陷仍在）。

### P3-8　文档与代码漂移

`Doc/PERM-魔方多租户架构.md` 附录标注 `WebMiddleware/TenantMiddleware.cs`，实际文件是 `DataScopeMiddleware.cs`（仓库中不存在 TenantMiddleware.cs）；文档主要示例仍以已标 `[Obsolete]` 的 `ITenantSource`/`TenantModule` 为主角。文档是新团队理解多租户的第一入口，建议随代码同步修订。

### P3-9　成员关系变更与令牌生命周期未联动

JWT 不含 TenantId 是合理取舍（支持多租户自由切换），代价是租户状态必须逐请求校验——这点当前做得对。但 `TenantUser` 被禁用/移除后，已颁发令牌在过期前只靠逐请求的 DB 校验拦截，建议把成员关系变更纳入令牌吊销触发点（jti 黑名单或 UserToken 失效），形成闭环。

## 三、TenantId=0 与空值的语义：为什么不能"全部置 0"来避免不可用

### 3.1　现状语义盘点：0 不是"默认租户"，是"管理后台/不受限"哨兵

代码中并不存在"默认租户"的概念，`TenantId == 0` 的含义是**管理后台模式（不做任何租户过滤）**，`Tenant` 表里也不存在 Id=0 的记录（自增从 1 开始，`ResolveTenantById("0")` 直接短路返回、不查库）。系统管理员确实以 `TenantContext.TenantId == 0` 运行，含义是"不受租户限制、可见所有租户数据"。`TenantContext.TenantId` 的注释原文即："0表示进入管理后台，没有进入任意租户"。

散落的 `== 0` 特殊分支至少八处：

| 位置 | 0 的语义 |
|------|----------|
| `TenantContext.CurrentId` | `Current?.TenantId ?? 0`——null 与 0 在此合一 |
| `ResolveTenantById` | 0 直接放行，不校验租户存在性 |
| `ChooseTenant` | 0 仅系统管理员可进入；普通用户被强制改判到第一个有效租户 |
| `DataScopeMiddleware` | 非管理员 + tenantId==0 → 403「无权访问该租户」 |
| `ValidateTenant` | 普通用户必须 CurrentId > 0 |
| `CreateWhere` | 0 → 不加过滤（管理后台看全量）；null → fail-closed `1=0` |
| `TenantInterceptor.OnValid` | ctx==null 或 0 → 跳过写路径校验；`OnCreate` 在 ctx!=null 时无条件赋 ctx.TenantId → **管理后台模式新建的行 TenantId=0** |
| `EnsureTenantUser` / `ApplyTenant` | <=0 → 不补建绑定 / 不过滤 |

### 3.2　空值（null）的含义

- **请求层**：不带任何租户信息 → `GetTenantId` 应返回 -1（当前因 P0-1 变成 NRE）。
- **上下文层**：`TenantContext.Current == null` 表示未设置。多租户开启时触发 fail-closed——CreateWhere 拼 `1=0`、ValidateTenant 拒绝普通用户。注意 `CurrentId` 把 null 折叠成 0，部分代码用 `Current`、部分用 `CurrentId`，两者判空语义并不等价（又一处 P1-5 隐患）。
- **数据层**：`TenantId` 字段是非空 Int32，"空"在库里表现为 0——开启多租户之前的存量行、以及管理后台模式新建的行。这些行对租户用户不可见（按 `TenantId=N` 过滤），只有管理后台模式（不过滤）可见。

### 3.3　"把存量用户/数据初始化成租户 0"的影响分析

结论：**四条路径全部走不通**，0 不能被复用为"默认租户"。

1. **用户层面没有"租户 0"可绑**：用户本身没有 TenantId 字段，成员关系是 `TenantUser` 行；`TenantUser.TenantId=0` 指向不存在的租户记录。
2. **让普通用户进入"租户 0"上下文**：`DataScopeMiddleware` 对非管理员 + tenantId==0 明确返回 403——依旧锁死，问题原封不动。
3. **放宽该校验让普通用户以 0 通行**：0 在 CreateWhere/TenantInterceptor/ApplyTenant 的含义是"不过滤"——每个普通用户都将看到**所有租户的全部数据**，数据隔离彻底失效。0 是"旁路信号"，与"默认租户"在语义上互斥。
4. **只把存量数据行保持/回填为 TenantId=0、用户绑真实租户**：租户用户按 `TenantId=本租户` 查询，存量行（0）永远不可见，只有管理后台可见——数据变成管理员专属孤岛，等于丢了存量数据。
5. **语义过载风险**：一个魔法数字同时承载"不受限"与"默认租户"两种含义，上表八处分支的语义被静默改写——这是 P1-5 问题的放大版，任何后续维护者都可能读错。

### 3.4　正确做法：真实默认租户（Id≥1），及其影响

做法：首次开启多租户时创建**真实默认租户**（如 Code="default"，Id 自增 ≥1），批量绑定存量用户（TenantUser），并把各业务表的存量行（TenantId=0）回填为默认租户 Id。0 继续保留"管理后台/不受限"的单一含义。影响与注意事项：

- **一次性迁移成本**：一条 Tenant + N 条 TenantUser + 每张 ITenantScope 表一条 UPDATE。换来的是开启瞬间无人锁死、存量数据对原用户可见。
- **存量 0 行需逐表甄别**：若某些表的 TenantId=0 行是有意为之的"全局共享数据"，不能一刀切回填进默认租户，否则共享数据被私有化。迁移脚本必须按表确认。
- **管理后台新建数据的归属要决策**：开启多租户后，管理员在管理后台模式（0）创建的行仍会被 `TenantInterceptor.OnCreate` 打上 TenantId=0，对租户用户不可见。需要明确策略：管理员创建的是"全局数据"（保持 0，仅管理后台可见）还是代某个租户创建（应切到该租户上下文再操作）。
- **默认租户是拆分前的"暂存池"**：后续引入真实租户时，用户与数据要显式迁出默认租户；建议提前设计拆分流程（按组织/按业务线），避免默认租户无限膨胀成第二个"大杂烩"。
- **跨租户统计**：管理后台（0 不过滤）天然可见全量，报表场景不受影响；如需在非 0 上下文跨租户查询，按第四节第 3 条提供显式 scope。

## 四、行业成熟改造方案

### 1. 租户解析层：单一入口 + 策略链 + 结果对象

把散落在 GetTenantId/ChooseTenant/DataScopeMiddleware 里的解析收敛为唯一的 `TenantResolutionMiddleware`，产出结构化结果而不是裸 Int32：

```csharp
public enum TenantResolutionStatus { Disabled, None, Invalid, Resolved }

public class TenantResolutionResult
{
    public TenantResolutionStatus Status { get; init; }
    public Int32 TenantId { get; init; }        // 0=管理后台
    public Tenant? Tenant { get; init; }
    public String? FailureReason { get; init; }  // 供统一错误输出
}
```

解析来源做成策略链（`ITenantResolutionStrategy`）：HeaderStrategy（X-Tenant Code）→ HeaderIdStrategy（兼容期）→ QueryStrategy → CookieStrategy，未来可平滑追加 **SubdomainStrategy（tenant1.example.com）和 PathStrategy（/t/{tenant}/...）**——这两种是行业 SaaS 的标准形态，当前的单函数 if 链无法扩展。每个策略 null-safe，任何来源缺失都返回"未提供"，绝不抛异常。解析结果写入 `HttpContext.Features`，下游只消费、不再二次解析。`Tenant`/`TenantUser` 查找走 `IMemoryCache`（实体保存时失效），消除逐请求 DB 往返。

### 2. 上下文传递：DI scoped 服务替代静态全局

```csharp
public interface ITenantContext
{
    TenantMode Mode { get; }        // None / AdminBackend / Tenant —— 用枚举消灭 0/null 魔法值
    Int32 TenantId { get; }
    Tenant? Tenant { get; }
}
services.AddScoped<ITenantContext, TenantContext>();
```

只有解析中间件写、其余组件只读。XCode 层如需保留 AsyncLocal（它不依赖 ASP.NET DI），也由中间件做**唯一一次**同步。这样单元测试不再需要清理静态状态，`TenantMode` 枚举让"管理后台"成为类型系统里的一等公民，`if (mode == TenantMode.AdminBackend)` 比 `if (tenantId == 0)` 不可能读错。

### 3. 数据隔离：保留 XCode 单层权威，策略可配置

纵深防御保留，但明确**数据层以 XCode 全局过滤为唯一权威**：控制器层 `CreateWhere` 里的手工字符串拼接（`"TenantId={#TenantId}"`、`"1=0"`）降级为断言/兜底日志，避免两套过滤逻辑各自演化。fail-closed 做成策略配置：

- `DenyWithEmpty`（现状）：适合对可用性不敏感的内部系统；
- `ThrowOnMissingTenant`：显式抛错，适合对外 API，让客户端拿到明确错误而不是"假空数据"；
- 另提供显式跨租户 scope（类似 EF Core 的 `IgnoreQueryFilters`），供管理后台报表使用：

```csharp
using (TenantScope.Ignore())   // 仅系统管理员可获取，内部断言
{
    var all = Order.FindAll();
}
```

### 4. 存量迁移：默认租户 + 自动回填 + 影子模式（解决 P0-2 的根本方案）

行业通用的三步走（0 值不可用的原因见第三章）：

1. **默认租户**：首次开启多租户时（迁移脚本或首启任务）自动创建"默认租户"（**真实租户，Id≥1，绝不能是 0**），把全部存量用户批量绑定为 `TenantUser(Enable=true)`。存量业务数据（TenantId=0 的行）按表甄别后回填为默认租户 Id。这样开启瞬间没有人被锁死，也没有孤儿数据。
2. **登录自动绑定（有租户信息时）**：`EnsureTenantUser` 已具备补建能力（各登录路径都会调用）。多租户开启后，存量用户登录且**携带有效租户标识（X-Tenant/X-App-Id）**时，`EnsureTenantUser` 自动补建 `TenantUser` 绑定；**无任何租户信息时不做绑定处理**（影子期仅按第五章规则 A 放行并记录影子日志）。存量绑定的可靠批量来源是一步性的迁移脚本（第 1 条）——若漏跑迁移脚本且客户端始终不带租户标识，登录无法自愈，切 Enforce 前必须补齐迁移。
3. **影子模式灰度**：`EnableTenant` 增加伴生开关 `TenantEnforceMode = Shadow | Enforce`。Shadow 模式下全部租户校验只记录日志不拦截，先跑一到两周观察"哪些请求会被拒"，确认无误伤再切 Enforce。这是 feature flag 灰度发布的标准做法，能把"开关一打开全员锁死"这类事故从不可接受变为可回滚。**Shadow 期同时承载新旧客户端兼容规则（旧客户端放行、新客户端自动绑定），详见第五章兼容性补丁。**

### 5. 统一错误语义 + ProblemDetails

定义统一的租户错误契约（HTTP 层按 RFC 7807 ProblemDetails 输出）：

| 场景 | 建议 |
|------|------|
| 需要租户但未提供 | 400 + `tenant_required` |
| 租户不存在/已禁用 | 400 + `tenant_invalid` |
| 用户不属于该租户 | 403 + `tenant_forbidden` |
| 未登录 | 401（现状保持） |

五处分散校验收敛为一个 `TenantAccessPolicy.Evaluate(user, resolution)`，中间件、认证、控制器只是在**不同阶段**调用同一个策略——语义从此只有一份。同时修复 NRE 后补一条约定：**解析层永不抛异常，策略层永不写响应副作用**（把 SaveTenant 从 ChooseTenant 挪到显式的登录/切换动作里）。另需修复 NRE 被计入登录风控错误次数的次生问题（异常不应走 HandleLoginError 计数）。

### 6. 可测试性与可观测性

- 本次 `TenantAuthReproTests` 开了很好的头，建议固化为**租户矩阵集成测试**（模式 × 身份 × 租户来源 × 启用状态）进 CI，任何租户相关改动必须过矩阵；具体分层见第七章。
- 日志/Trace 全量附 TenantId（DefaultSpan.AppendTag 已起步），并把"被 fail-closed 拒绝"作为独立埋点——它是误伤存量用户的最早预警信号。

## 五、兼容性补丁：影子期旧客户端放行与新客户端自动绑定（v1.2 新增）

改造方案发版之后，客户端生态必然经历一段过渡期：**旧客户端**（不感知多租户，请求不带任何租户标识）与**新客户端**（请求携带租户标识——头部 X-Tenant，或微信体系登录携带 appid）并存。本章定义这段过渡期的兼容性补丁：由影子开关（第四章第 4 条的 `TenantEnforceMode`）统一控制，迁移完成后**全部移除**。

### 5.1　开关与生命周期

复用第四章第 4 条的影子设置，不新增独立开关，避免开关组合爆炸：

| TenantEnforceMode | 含义 | 兼容性补丁 |
|------|------|------|
| Shadow | 兼容观察期：不拦截，按本章规则放行并记录全局日志 | 生效 |
| Enforce | 全面生效：fail-closed，拒绝无租户标识的请求 | 成为死路径，等待移除 |

生命周期三段：`Shadow（兼容 + 观察）` → `Enforce（全面生效，旧客户端被拒）` → `移除全部兼容代码`。兼容逻辑只存在于前两段之间，**代码注释中必须明示"后期将全部移除"**（见 5.4）。

### 5.2　规则 A：无租户标识的请求（旧客户端）照旧逻辑放行

判定：请求不带 X-Tenant / X-Tenant-Id / X-App-Id / Query tenantId / 租户 Cookie 中的任何一种（即 GetTenantId 解析不到租户、也不是携带 appid 的微信/SSO 入口）。

处理（仅 `EnableTenant && TenantEnforceMode == Shadow` 时生效）：

- **认证层**：`ValidateTenant` 对此类请求跳过 fail-closed——未绑定的存量用户直接放行，不设置租户上下文；
- **数据层**：`CreateWhere`/`TenantInterceptor` 对无租户上下文的请求不加租户过滤，等同多租户开启之前的行为；
- **已绑定用户**：`ChooseTenant` 按现有逻辑回落到"第一个绑定租户"，不报错（该行为当前已存在，补丁不改变它）；
- 全程不抛异常、不返回 401/403/400——旧客户端对改造无感知。

**影子日志（必选）**：每次兼容放行写全局日志（LogProvider/XTrace，带统一标签），内容包含请求路径、用户、来源 IP、"旧客户端无租户标识，兼容放行"。这份日志是评估"何时可以安全切换 Enforce"的唯一量化依据。

**安全权衡（显式接受）**：这是迁移窗口期内的**临时 fail-open**——无租户标识的请求将看到未经租户过滤的数据。接受它的理由：(1) 开启多租户之前所有请求本来就处于这种状态，兼容期不劣化于旧系统；(2) Shadow 期全程有日志可观测、可统计；(3) 切换 Enforce 后即恢复 fail-closed。为防止窗口期被无限拖延，必须设定移除时间线（见 5.5）。

### 5.3　规则 B：带租户标识的请求（新客户端）首次登录/注册自动绑定

新客户端判定：请求携带 X-Tenant（租户编码），或微信/SSO 体系登录携带 appid（`X-App-Id → OAuthConfig.FindByAppId → config.TenantId`，与 `ResolveRegisterTenant` 同一套来源约定）。

处理分两个场景：

1. **发版后首次登录（存量用户自动绑定）**：登录认证通过后，按请求携带的租户标识检查 `TenantUser`——**数据里没有绑定、但请求带了租户信息**，即自动创建 `TenantUser(Enable=true)`，随后 `ChooseTenant` 落位、正常颁发令牌。实现上即 `EnsureTenantUser` 的兜底增强：解析到有效租户标识且用户未绑定时补建绑定，记录 CreateIP/CreateTime 并写审计日志（"存量用户自动绑定租户"）。注意一处统一：`EnsureTenantUser` 目前只经 `GetTenantId` 解析（不识别 X-App-Id），补丁中应与注册入口对齐为**"优先 X-App-Id、其次 X-Tenant"**，同时覆盖头部带租户编码与微信 appid 两种新客户端形态。
2. **新注册**：`ResolveRegisterTenant` 已强制要求 X-App-Id/X-Tenant 并设置租户上下文，`CompleteLogin → EnsureTenantUser` 创建绑定——现状已满足，补丁保持不变。
3. **关于"用户表更新租户 id"**：当前数据模型中，用户↔租户的成员关系以 `TenantUser` 关联表为唯一事实来源，User 表本身**没有 TenantId 字段**（这是支持一个用户归属多个租户的正确模型）。推荐维持该模型——兼容补丁自动维护 TenantUser 即完成"用户与租户的关联"。若业务确实需要在 User 表上携带"主租户"，则新增 `User.TenantId` 字段并在兼容逻辑中同步更新，但必须注明其语义为"最近绑定/主租户"，仅作展示与默认落位用，不参与成员资格判定，避免多租户用户语义冲突。

### 5.4　代码注释与标识规约

所有兼容代码使用统一注释标签，便于生命周期结束时全局检索、一次性移除：

```csharp
// [TenantCompat] 兼容逻辑（Shadow 期）：旧客户端无租户标识，照多租户开启前的旧逻辑放行，
// 不拦截、不报错，仅记录影子日志。TenantEnforceMode 切换 Enforce 并稳定后全部移除（计划 vX.Y）
if (set.EnableTenant && set.TenantEnforceMode == TenantEnforceModes.Shadow && tenantId < 0)
{
    XTrace.WriteLine("[TenantCompat] 旧客户端兼容放行：{0} {1}", ctx.Request.Path, user?.Name);
    return true; // 跳过 fail-closed
}
```

规约要求：

- `[TenantCompat]` 标签全仓库唯一，不得用于任何非兼容代码，`grep [TenantCompat]` 即得完整移除清单；
- 每处兼容分支必须同时包含影子开关判断与影子日志，不允许"静默兼容"；
- 兼容代码集中在租户解析/认证链路（GetTenantId、ValidateTenant、EnsureTenantUser、CreateWhere 兜底），禁止散落进业务控制器与实体代码；
- 注释中写明移除预期（计划版本号），与 5.5 移除准则呼应。

### 5.5　移除准则（退出条件）

1. **量化指标**：影子日志统计"无租户标识旧客户端"请求占比持续低于约定阈值（如 <0.1%）并维持约定天数（如 14 天）；
2. **切换 Enforce**：`TenantEnforceMode=Enforce`，旧客户端请求开始被 fail-closed 拒绝——这是预期行为，倒逼剩余未升级客户端完成升级；观察拒绝日志与用户反馈一个窗口期；
3. **代码移除**：Enforce 稳定后，删除所有 `[TenantCompat]` 标签代码、兼容分支及相关影子日志埋点；第七章中的兼容性测试同步删除或转为常规回归用例。

## 八、实施落地记录（三段式 + 关键决策）

本节记录已实施的三段式设计与各项决策，作为"代码与方案是否统一"的核对基准。

### 8.1 三段式职责分离（已实施）

```
请求 →
① 认证（纯身份）：JWT→jti→UserToken→user，token 校验不掺任何租户判断
② 租户解析（DataScopeMiddleware）：只解析租户上下文（GetTenantId→SetTenant），
   不做成员校验；无效显式标识→400；Shadow+无标识→放行+影子日志
③ 成员授权（TenantAccessPolicy.IsMember，唯一授权点）：由认证后的 ValidateTenant 调用；
   管理员豁免；普通用户须有指定租户的有效 TenantUser 绑定；
   显式携带租户标识（X-Tenant/X-App-Id/Query/Cookie）时**按该租户校验成员**（非成员→403），
   仅无标识时才回落第一个绑定租户（Shadow 规则A 兼容放行）
```

- **中间件不再做成员校验**：原中间件依赖 `ManageProvider.User` 加载时机做成员校验，导致"新令牌刚签发首请求"时序抖动（M5）。已移除，成员校验收敛到 `TenantAccessPolicy`（`ValidateTenant` 调用），语义只有一份（对应 §4.2）。
- **`TenantAccessPolicy.IsMember(tenantId, user)`**：管理员豁免（可进管理后台 tenantId=0 及任意租户）；普通用户 tenantId<=0 拒绝、tenantId>0 查 TenantUser 有效性。

### 8.2 关键决策（已定）

| 决策点 | 决策 | 说明 |
|--------|------|------|
| 影子开关 | `TenantEnforceMode`：Shadow（默认）/Enforce | Shadow 兼容观察期，Enforce 严格 fail-closed |
| 注册（Shadow） | 无租户标识**可注册**（不绑定，规则A放行）；带标识→自动绑定 | 与登录规则A对称 |
| 注册（Enforce） | 无租户标识**拒绝**；带标识→绑定 | `ResolveRegisterTenant` |
| 登录租户选择 | 带租户→用它（**按所带租户校验成员**）；不带→上次登录租户→兜底第一个绑定租户 | `ChooseTenant`；显式标识优先校验（见下"非成员访问"） |
| **管理员无租户标识** | **豁免**，直接进管理后台（tenantId=0），无需租户标识 | 管理员本身不属任何租户；Enforce 下也放行（`ValidateTenant` 先于 ChooseTenant 判断，避免普通用户被回落漏拒） |
| 非成员访问某租户 | **显式标识优先校验**：显式携带租户标识时按该租户校验成员——管理员豁免但**上下文用所带租户**（不再落管理后台看全量）；普通用户非成员→**403「无权访问该租户」**；**仅无标识时**才回落第一个绑定租户（200） | 收敛到授权层 `ValidateTenant`（唯一授权点，对应 §4.2）；修复了"显式请求 t2 被静默换 t1"与"管理员带 X-Tenant 落全量"两个契约问题（2026-08-16 更新） |
| 迁移脚本 | **不做**（用户否决） | 存量兼容靠影子期 + 自动绑定 |

### 8.4 已知边界（非缺陷，已确认）

- **显式非成员访问某租户 → 403**（已收敛到授权层，2026-08-16 更新）：普通用户显式携带非成员租户标识被拒；无标识场景下 Shadow 规则A 仍回落第一个绑定租户（兼容放行，不拒绝）。
- **X-App-Id 两阶段优先级差异**：中间件不解析 X-App-Id（只认 X-Tenant/Query/Cookie），认证层 `ResolveTenant` 优先 X-App-Id（OAuth 配置租户）。同时携带"无效 X-App-Id + 有效 X-Tenant"时中间件按 X-Tenant 设上下文、认证层按 X-App-Id 拒绝（错误出口 400 vs 403 不一致）——属既定设计，正常客户端不会同时携带两套标识。
- **XCode EntityCache 10s TTL**：新插 Tenant/TenantUser/UserToken 行短暂不可见，外部 sqlite 改库须等 TTL 或重启。
- **首个真实注册用户成为管理员**：占位 admin/admin 被降级游客并禁用；验证管理员场景须用首个注册用户。
- **配置缓存**：直接改 Parameter 表会被落盘到 `Bin/CubeDemo/Data/dbConfig_Cube.json`，删库重建仍继承旧值，须一并删除该缓存文件。

## 附：一句话结论

数据隔离的安全设计（fail-closed、纵深防御、AsyncLocal 修复）已达到行业合格线以上；当前真正的短板在**工程化闭环**——解析层一个空引用、开启开关没有迁移路径、五处校验五种语义。按上述路线图补齐"单一解析入口 + 默认租户迁移（真实租户，不用 0）+ 统一错误契约"三件事后，这套方案可以称得上成熟的行级隔离多租户架构。
